# Whole-repo review queue

This configuration bundles `repo-review` (`lisp/repo-review.el`, standalone, wired in
by `init-review.el`) for a review of a complete repository rather than a
diff. It builds a per-project Org queue with one `TODO` headline per
project file; you open each file read-only, annotate it, and mark the
headline done. The package never changes the reviewed sources.

## Entry point: `C-x p R`

`C-x p R` (or `M-x repo-review-start`) opens the current project's
queue, building it on first use. The file list comes from
`project-files`, so `.gitignore` applies and untracked files are
included. A prefix argument (`C-u`) asks for confirmation, discards all
review state, and rebuilds the queue; `g` (`repo-review-refresh`)
appends files added since the queue was built without touching existing
headlines.

Each project keeps its own queue under `var/repo-review/`, named after
the project directory and a hash of its path. The first line of the
queue file sets the major mode, so the queue keys come back when you
reopen it; the `#+review_root:` keyword records the project root and
each headline keeps its project-relative path in the `REVIEW_PATH`
property.

## Pull requests and merge requests: `C-x p V`

`C-x p V` (`repo-review-pullreq`) opens a queue for a Forge pull request
(GitHub) or merge request (GitLab). Run it in a Forge topic buffer on the
request, or anywhere in the project and enter the number. The queue lists
the files the request changes against its merge base. `RET` shows a file
as a read-only diff, never as a checkout, so the working tree stays as it is.
The revisions must exist locally: run `forge-pull` or fetch the request
first, otherwise the command reports the git error.

Each request has its own queue file (`<project>-<hash>-pr<N>.org`) and
notes file. Opening the same request again reuses the queue and its state.
`e` opens the file as it is in the working tree.

### Comments

In a diff buffer, `c` (`repo-review-comment`) asks for a comment on the
added or unchanged line at point and saves it as a draft: a `Draft` sub-headline
under the file in the queue, with the line in the `DRAFT_LINE` property.
Nothing leaves your machine. Edit or delete a draft as ordinary Org text.
Comments on removed lines are not supported.

`P` in the queue (`repo-review-post-comments`) lists the unposted drafts and asks
`yes-or-no-p` before it sends them, one request each, through Ghub with the
Forge token. GitHub gets a review comment on the pull request. GitLab gets a
discussion on the merge request, with the diff position taken from the merge
base. A posted draft gets a `POSTED` property and is never sent again. If a
request fails, the drafts before it stay marked as posted and the rest stay
drafts. The default `repo-review-post-function` refuses to run in a batch
session. The queue records the forge, repository and revisions in its header
keywords, so posting works after you restart Emacs. If the request moved on
(a force push), delete the queue file and open the request again before you post.

## Queue keys

| Key | Command | What it does |
| --- | --- | --- |
| `RET` | `repo-review-visit` | Open the file at point in another window, read-only in `view-mode` |
| `e` | `repo-review-visit-writable` | Open the file at point for editing |
| `n` / `p` | `org-next-visible-heading` / `org-previous-visible-heading` | Next / previous headline |
| `N` | `repo-review-next-todo` | Next headline still in the `TODO` state and not viewed |
| `t` | `org-todo` | Change the state: `TODO`, `REVIEWING`, `DONE`, `SKIP` |
| `P` | `repo-review-post-comments` | Post the draft comments of a pull request queue after a confirmation |
| `v` | `repo-review-toggle-viewed` | Toggle the viewed tag of the file at point |
| `m` / `u` | `repo-review-mark-viewed` / `repo-review-unmark-viewed` | Mark the file at point as viewed / remove the mark |
| `A` | `repo-review-ai-check-draft` | Ask gptel for advice on the draft comment at point |
| `g` | `repo-review-refresh` | Append files new in the project since the last scan |
| `/` | `org-sparse-tree` | Filter, for example to show only `TODO` files |
| `q` | `quit-window` | Close the queue window |

In a file opened with `RET`, the `view-mode` key `e` makes the buffer
writable.

## AI assistance with gptel

gptel is optional. Without it everything above works, and the two commands below
report that gptel is missing. In a pull request diff, `a` (`repo-review-ai-draft-comment`)
sends the hunk at point to the gptel model and opens the answer in the minibuffer
for you to edit. The draft is saved only when you accept it. On a draft in the queue,
`A` (`repo-review-ai-check-draft`) asks the model for advice on clarity and tone and shows
it in a buffer, and leaves the draft as it is. Both commands send diff or comment text
to the provider that gptel uses, and neither one posts. Set `repo-review-ai-function`
to use another client, and `repo-review-ai-max-chars` to limit the hunk size.

## Viewed state

`v` toggles the `viewed` Org tag on the file at point, `m` marks it and `u` removes the mark.
The header line of the queue shows how many files you viewed. The tag is in the queue
file, so it persists with the review: it survives a restart, `g`, and a change of the
`TODO` state, which is separate. Marking a file also records its content in the
`VIEWED_REV` property (the SHA-1 of the file, or the blob at the head revision in a pull
request queue). When you open the queue or press `g`, a file whose content differs
from that record loses its mark, like a changed file on GitHub. `N` skips viewed files.
The keys also work in a pull request diff and in a file opened from the queue (they act
on the queue entry of that file). Use `/` with the tag match `viewed` to list
viewed files. Set `repo-review-mark-viewed-on-visit` to mark a file when you open it.

## Marginal notes with org-remark

Files visited from the queue enable `org-remark-mode` (bundled).
Highlights and comments collect in a per-project notes file beside the
review queue (`<project>-<hash>-notes.org`), never in the source tree.
Set `repo-review-use-org-remark` to nil to visit files without
annotation support.

## Options

| Variable | Default | Effect |
| --- | --- | --- |
| `repo-review-queue-dir` | `var/repo-review/` | Directory for the per-project queue and notes files |
| `repo-review-source-extensions` | nil | Lowercase extensions (no dot) to include; nil queues every file |
| `repo-review-exclude-regexp` | nil | Regexp matched against project-relative paths to leave out |
| `repo-review-post-function` | `repo-review--ghub-post` | Function that sends one comment request to the forge |
| `repo-review-mark-viewed-on-visit` | nil | Mark a file as viewed when you open it from the queue |
| `repo-review-ai-function` | gptel | Function that sends a prompt to the language model |
| `repo-review-ai-system-prompt` | reviewer prompt | System prompt of the AI commands |
| `repo-review-ai-max-chars` | 20000 | Longest hunk text the AI commands send |
| `repo-review-use-org-remark` | t | Enable `org-remark-mode` in visited files |

## Safety

Queue files record project-relative paths in the `REVIEW_PATH` property.
Absolute paths and paths containing `..` that escape the review root are
rejected when opening a file. Hand-edited queue files must keep all paths
relative to the project root.

Deleted files stay in the queue; mark their headlines `SKIP`.
